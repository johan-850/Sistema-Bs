## Objetivo

Que el negocio abra el sistema desde una dirección web, sin instalar nada, con configuración separada entre pruebas y producción.

## Por qué está acá y no antes

Publicar temprano suele ser lo correcto: encuentra problemas de rutas, de variables de entorno y de rendimiento real que en local no aparecen. La razón de dejarlo en el penúltimo sprint es puramente aritmética — adelantarlo dejaba sprints de 38 SP o más.

**Si en algún momento quieres verlo publicado antes, este sprint se puede mover sin tocar ningún otro.** No tiene dependencias técnicas.

## Decisión pendiente: dónde se hospeda

`USB-031` requiere elegir proveedor. **Es una decisión tuya, no mía**: depende de costo, de si ya usas algún servicio y de dónde está el negocio.

El resultado de `flutter build web --release` es un sitio estático (`build/web/`), así que sirve cualquier hospedaje de sitios estáticos. Las opciones razonables:

| Opción | A favor | En contra |
|---|---|---|
| **Vercel / Netlify** | Gratis para este tamaño, HTTPS automático, despliegue desde git | Un servicio más que administrar |
| **Cloudflare Pages** | Gratis, muy rápido en Latinoamérica | Ídem |
| **Supabase Storage** | Todo queda en un solo proveedor, ya lo pagas | No está pensado para servir sitios; sin dominio propio cómodo |
| **Servidor propio del negocio** | Funciona sin internet externo, útil si la conexión es mala | Hay que administrarlo, y no hay HTTPS trivial |

Vale la pena considerar el último caso: **si el negocio tiene internet inestable, un sistema web hospedado afuera se cae con la conexión.** Servirlo desde una máquina de la propia tienda cambia esa ecuación — aunque Supabase seguiría siendo remoto, así que la venta igual requiere conexión. Si eso es un problema real, el modo sin conexión es una funcionalidad aparte que no está en este backlog.

## Enfoque por historia

### USB-031 — Publicar (5 SP)

Configurar el proveedor elegido, compilar en modo release y publicar con HTTPS. Documentar el procedimiento en el README para que sea repetible.

### USB-032 — Configuración por ambiente (5 SP)

Hoy `.env` es un asset que se empaqueta dentro del build (`pubspec.yaml`), así que **el proyecto Supabase queda fijado en tiempo de compilación**. Separar pruebas de producción significa dos builds con dos `.env` distintos, no una variable en tiempo de ejecución.

Conviene evaluar `--dart-define` en el build de producción en vez del asset: mantiene las credenciales fuera del bundle de assets y encaja mejor con un despliegue automatizado. Es un cambio pequeño en `main.dart`.

Las credenciales no quedan en el repositorio en ningún caso.

Prioridad baja: es comodidad, no funcionalidad.
